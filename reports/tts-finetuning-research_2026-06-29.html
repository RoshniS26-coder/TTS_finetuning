1Architecture & why eval/loss is a weak signal

VERDICT. Parler-TTS is an autoregressive decoder LM over DAC audio-codec tokens, conditioned on a frozen Flan-T5 text encoder via cross-attention, trained with a plain cross-entropy objective. There is no mel-spectrogram loss and no GAN/discriminator loss (those belong to VITS/HiFi-GAN). Because the loss is token cross-entropy over a 9-codebook RVQ stack — and many token sequences decode to perceptually equivalent audio — eval/loss flattens early and is a weak proxy for perceived quality. Trust your ears + the audio-metric panel.

Why the loss number under-reports quality

  • Token CE ≠ perceptual quality. The 9 RVQ codebooks are predicted in parallel; codebook 0 (coarse) is learnable, higher codebooks stay near-random-ish (~4.7–4.8 nats) for every run — they barely move with fine-tuning, dragging the mean loss to a flat plateau.
  • Many valid renderings. Several token paths decode to perceptually identical speech, so a "wrong" next-token prediction is often not an audible error — CE penalizes it anyway.
  • The base model already saw ~45k h. Fine-tuning re-anchors voice/style rather than learning audio from scratch, so loss only inches down while the audible voice can shift a lot.
  • Practical rule (CLAUDE.md): stop when eval/loss rises while train/loss still falls; otherwise let logged audio + the metric panel decide.

Refs: Parler/Stable-TTS (arXiv 2402.01912); DAC neural codec (arXiv 2306.06546); Parler-TTS training README.

2.5 Convergence & epochs

  • Both runs plateau by ~1–2 epochs (≈ step 600–800). v5's curve is essentially flat from step 700 (4.6148 → 4.6135 at 988); extra epochs buy almost nothing on the loss axis — consistent with the HF README's 4-epoch worked example and the "per-speaker coverage is the binding constraint" point from the brief.

  • ⚙ Recommendation: for the v5 corpus, 3–4 epochs with early-stop on the eval-loss elbow is the right budget; spend saved compute on listening + the metric panel, not more steps.

3The disk-full failure & the fix

Root cause — checkpoint rotation 2× disk spike The one failed run in this project, toasty-fog-25 (id vz6mq40v, state=failed), died at step 600 = 2× save_steps (300). run_parler_tts_training.py is a manual accelerate loop, NOT the HF Trainer → it ignores save_strategy and honors only integer save_steps. On a save tick, rotate_checkpoints writes the new full-state checkpoint (~10 GB: model + AdamW optimizer state) before deleting the old one → a transient 2× (~20 GB) spike that fills a small volume → "No space left on device".
The fix (v5, in marathi_config.json) Set save_steps: 100000 (≫ the ~1000 total steps of a run) with save_total_limit: 1. The save condition cur_step % save_steps == 0 or cur_step == total_train_steps then fires only at the very end, so no intermediate checkpoints are written and the disk never doubles. The final model is still always persisted via unwrapped_model.save_pretrained(output_dir).
⚙ Trade-off: no mid-run resume — if the pod dies, just relaunch the accelerate launch command (by design, since no checkpoint exists).

Note on copper-voice-22: referenced in some prior notes but not found in project parler-speech — it is likely in another project or was deleted. It is recorded here as "not found" rather than fabricated.

Disk facts (RunPod, from CLAUDE.md)

  • /workspace is MooseFS → df -h /workspace shows the whole cluster (~PB) and is useless; use du -sh /workspace for real usage and df -h / for the container overlay disk.
  • Peak run usage: ~20 GB on /workspace, ~10 GB on the container disk → a 50 GB volume / 30 GB container is comfortable.
  • Stopping a pod wipes the container disk (pip deps + ~/.cache base model) — only /workspace persists.

4Dataset & speaker balance

VERDICT. Multi-speaker Parler is driven by name-anchored captions — the speaker name in the caption is the only identity label. Mixing voices under one unlabeled caption averages them into a mush; class imbalance lets the high-resource speaker dominate. v5 fixes both by capping Maya, cleaning data, and oversampling the low-resource target Sunita. Crucially, Sunita is a built-in Indic-Parler Marathi speaker, so v5 adapts a stable existing voice rather than building one from scratch — far safer at ~10 min of target audio.

v2/v3 corpus was an older, larger unbalanced multispeaker set (~12.8k clips) with Maya dominating before the cleanup, which is exactly the imbalance v5 was built to remove.

4.2 Why balancing + Sunita oversampling

  • Imbalance favors high-resource speakers. Left uncapped, Maya's 7561 clips would dominate the gradient and pull the shared decoder toward her voice/style.
  • Oversampling the low-resource target helps. The literature shows oversampling improves naturalness for under-represented speakers while undersampling is harmful — so Sunita's 232 train clips are repeated ×2 (TRAIN only; the test split is untouched → no leakage).
  • Per-speaker split before merge. Each speaker is split 2% then merged, so test covers every voice and eval/loss is meaningful per-run.
  • ⚙ For a target with <1 h of audio, LoRA/PEFT is the recommended adaptation route (less catastrophic forgetting); v5 used full fine-tune because the combined corpus is ~10.5 h.

4.3 Name-anchored captions & "adapt not create"

All captions use the same template; only the name and pace differ. Sunita being a real Indic-Parler Marathi speaker means we re-anchor an already-stable timbre — the lower-risk choice the model card and CLAUDE.md both recommend over inventing a brand-new name. Do NOT run fix_maya_caption.py (it flips Maya's caption from "moderate" to "fairly fast", desyncing pace).

Refs: ai4bharat/indic-parler-tts model card (named speakers incl. Sunita); oversampling/low-resource TTS (arXiv 1904.00771; arXiv 2502.07562; Kwon et al., Interspeech 2025).

5Evaluation metrics panel

VERDICT. No single number captures TTS quality. Use a battery: reference-free signal-quality metrics (UTMOS, SQUIM STOI/PESQ/SI-SDR) that run on novel stories now, plus human MOS/CMOS for the final call, plus identity (speaker-cosine), style (CLAP), and intelligibility (WER). MCD and classic PESQ need a time-aligned ground-truth reference, so they only apply to held-out clips that have the original recording — not to novel narrations.

How to populate each column
  • WER / CER: run the same held-out Marathi/Hindi text through each model, transcribe with Sarvam Saaras STT via scripts/narrate/compare_squim.py --wer, compare to reference (CER = char-level edit distance). distil-whisper is unreliable for Marathi → prefer Sarvam + relative deltas.
  • UTMOS: scripts/narrate/compare_squim.py (no-reference); already runnable on the existing model_outputs_v1/ baselines (gemini / indic_f5 / pretrained_indic_parler / mms).
  • MOS: human listening test, absolute 1–5.
  • CMOS: human blind A/B preference vs a fixed anchor (e.g. Gemini), −3…+3.
  • Speaker Sim: cosine similarity of ECAPA-TDNN (or x-vector) speaker embeddings between the generated clip and a Sunita reference clip.
  • RTF: wall-clock generation time ÷ output audio duration (lower = faster; <1 = faster than real-time).
  • Fairness rule: synthesize the SAME sentences with every model (SQUIM/UTMOS are per-clip), and run blind for MOS/CMOS.
Caveats to keep in mind
  • CLAP can stay high while audio degrades — it scores style match, not fidelity.
  • WER is unreliable in absolute terms for Marathi (distil-whisper is English-only); the repo's logged eval/wer sits ~100% and is best read as a relative signal across checkpoints, not an accuracy.
  • SQUIM is reference-free and was built for enhancement assessment → treat STOI/PESQ/SI-SDR as a relative comparator across models on identical texts, paired with UTMOS + listening.
  • MCD & classic PESQ require the original recording time-aligned to the output — usable only on held-out clips, never on novel generated stories.

5.3 How to benchmark vs Gemini-TTS

  1. Fix the text set. Pick N held-out Marathi paragraphs (mix seen-domain + unseen words).
  2. Generate from both systems on the same text: the v5 fine-tune (Sunita caption) and Gemini-TTS. Keep sample rate / loudness normalized.
  3. Run the identical objective panel on both sets: UTMOS + SQUIM (STOI/PESQ/SI-SDR) + speaker-cosine (to the v5 target) + relative WER. Tabulate side by side.
  4. Blind A/B CMOS. Present paired clips (ours vs Gemini) in random order to human raters; collect CMOS in −3…+3. This is the decisive metric.
  5. External anchor: Gemini 3.1 Flash TTS sits at ~1211 Elo on public leaderboards — a useful upper-reference, not a pass/fail bar. Success target: within ~0.2–0.3 MOS of Gemini on the Marathi target voice.

Tooling: scripts/narrate/compare_squim.py (TorchAudio-SQUIM STOI/PESQ/SI-SDR + UTMOS, no-reference; run on the RunPod GPU). Refs: TTSDS2 objective-metric battery (SSW 2025, minixhofer25); distil-whisper; Marathi-Whisper ASR (Lamarr); Gemini 3.1 Flash TTS.

6Inference caption-match rule

VERDICT. The inference caption MUST be byte-identical to the training caption. Voice identity and style are conditioned only through the frozen Flan-T5 cross-attention — it is the single conditioning channel, so any drift in the caption drifts the voice/style. (Mechanism-based, not a measured ablation.)

The exact v5 Sunita caption (build script CAPTION, name=Sunita, pace=moderate) — copy verbatim into test_inference.py and narrate_story.py DESCRIPTION:

Sunita narrates a children's story in an expressive, warm, animated storytelling tone with emotional variation, at a moderate pace. Very clear audio with no background noise.
  • Prosody is caption-driven, NOT transferred speaker→speaker. Sunita's intonation = her own clips + the caption's style words; the shared decoder only lifts general pronunciation.
  • The phrase "very clear audio" is the high-fidelity trigger — keep it. Punctuation (commas) in the Marathi transcript controls pauses/prosody — keep it too.

Refs: indic-parler-tts model card; Parler-TTS README.

7Recommendations / next steps

  • ⚙ Run the GPU metric panel on v5 outputs — UTMOS + SQUIM (STOI/PESQ/SI-SDR) + speaker-cosine to the Sunita target, on a fixed novel-story set. The local SQUIM run previously wedged on CPU; run it on the RunPod GPU.
  • ⚙ Do not rank v2 vs v5 by eval/loss. Their eval sets differ; settle it with blind listening + CMOS A/B.
  • Keep save_steps huge on every retrain (≫ total steps) to avoid the 2× checkpoint disk spike; accept no-resume.
  • Hold epochs at 3–4 for the v5-scale corpus; early-stop on the eval-loss elbow. Spend compute on data quality, not extra passes.
  • If targeting a <1 h voice, switch to LoRA/PEFT to reduce catastrophic forgetting; keep balancing + oversampling for the low-resource speaker.
  • Benchmark vs Gemini-TTS on identical text with the full panel + blind CMOS; aim within ~0.2–0.3 MOS of Gemini on the Marathi target.
  • Keep the caption byte-identical at inference; never edit name/pace/style words ad hoc.
